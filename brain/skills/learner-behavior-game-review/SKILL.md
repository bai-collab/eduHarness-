# 學習者行為與挑戰驗收

這個 Skill 研究「學生在介面上實際做了什麼」，把可觀察證據、合理假設、挑戰階梯與驗收證據接成一條可回溯的線。目標是讓學生需要自己找線索、做判斷、組合語句並從錯誤恢復，而不是把答案藏在卡牌、標籤或高亮效果裡。

它是 supporting Skill，不取代主 Skill 的 Route Plan，也不自行新增、刪除或重排 Route Plan 節點。主 Skill 已指定流程時，遵守主流程；本 Skill 只補上行為設計與驗收契約。

## 先確認範圍

啟動前先確認：

- 學習者是誰、學習目標是什麼、遊戲中的任務與成功條件是什麼。
- 要觀察的是群體或匿名情境的操作行為，不是替某個孩子貼上能力、個性或健康標籤。
- 是否包含 Web 介面、卡牌、拖放、句子組合、線索、NPC 對話或密室逃脫流程。
- 是否需要只做行為／難度設計，或還要做 DOM 驗收與 Chrome 視覺驗收。

若缺少會改變設計的年段、教材、學習目標或成功條件，只輸出 `intake-only` 與缺件，不猜測學生行為。若請求只有臨床、人格、注意力或個人監控，停止並說明本 Skill 不適用；不要把一次點錯解讀成診斷證據。

## 證據規則：先記錄，再解釋

每一筆判斷都要標記證據類型。可稽核摘要即可，不保存私有推理過程。

| 證據類型 | 可以支持的說法 | 不可以直接推出的說法 |
| --- | --- | --- |
| `dom_measurement` | 元件存在、文字可見、按鈕 disabled、矩形重疊、狀態有轉移 | 學生理解或不理解內容 |
| `interaction_trace` | 學生點了什麼、拖了幾次、在哪個狀態重試 | 學生懶惰、笨、沒有動機 |
| `screenshot_visual` | 看得到的層級、裁切、遮擋、提示位置 | 學生一定看懂畫面 |
| `teacher_report`／`student_report` | 使用者描述的困惑、偏好或阻塞 | 所有學生都會一樣 |
| `research_reference` | 已查證的設計原則或研究結果 | 這個班級一定符合研究平均 |
| `inference` | 帶有替代解釋的暫時假設 | 當成事實或診斷 |

寫行為假設時固定使用以下格式：

1. `觀察`：只寫可重現的操作或畫面證據。
2. `可能原因`：至少列兩個合理原因，例如線索不明、目標不可點、工作記憶負荷太高。
3. `可觀察預測`：若某原因為真，下一次會出現什麼操作證據。
4. `最小測試`：一次只改一個變因，例如只改提示位置，不同時改文字、顏色和答案。
5. `結果與決策`：保留、修正、回退或需要教師試用；沒有證據就保持不確定。

不要用「學生不會」「學生不專心」當結論。一次錯誤可能來自按鈕被遮住、答案順序已洩漏、提示位置太遠、語句負荷太高或學習者尚未理解任務。

## 學生不應直接拿到答案

把「提示」和「答案」分開審查。玩家畫面遵守以下規則：

- 指令說明要告訴學生要觀察的範圍、證據種類或下一個行動，不直接說出配對結果。例：「找出能打開出口的線索」可以；「鑰匙卡要拖到門上」不可以在尚未推理前直接出現。
- 選英文證物卡只能表現「卡牌已選」；不可讓對應物件發光、加粗、跳動、出現外框或自動捲到目標位置。
- 任何 `word → location`、`object → number`、`card → hotspot` 對照表只可存在於教師檢查、測試 fixture 或內部狀態，不可出現在玩家可見文字、ARIA 名稱、`title`、tooltip、`alt` 或可讀的隱藏內容。
- 線索可以分層：先給觀察方向，再給分類提示，再給句型框架；只有學生已嘗試且主動要求後，才提高提示層級。提高層級時標示「提示」而不是假裝仍是發現。
- 錯誤回饋說明錯在哪一類、下一步能做什麼，不直接補出正確答案。保留已完成進度，讓學生能重新嘗試。
- 被鎖住或 disabled 的控制項不可沉默。要說明「還缺什麼狀態」與「下一步去哪裡」，但不要把尚未發現的解法直接寫出來。
- 句子組合的詞塊預設打亂；完成區只顯示學生已放入的詞塊，不預先印出正確順序。需要支援時，可提供空格數、句首或詞性提示，不能直接排列完成。
- 若介面採雙欄，固定左側為案件／線索與分頁、右側為證物／對話／解鎖操作；學生讀線索時仍能看見目前操作區，不要求在兩個垂直區段間反覆捲動對照。窄畫面才堆疊時，要保留「先線索、後操作」的標題與順序。

### 本專案常見的答案洩漏反例

以下是審查標記，不是玩家提示：

- 點 `window` 卡後窗戶亮起：`BLOCK`，把搜尋任務變成看高亮。
- 畫面直接列出「學校牌 → one、鉛筆 → two、尺 → three」：`BLOCK`，學生只需抄答案。
- 拿到 `key` 後門沒有可辨識、可點擊或可恢復的狀態：`BLOCK`，這是狀態與回饋失敗，不是學生推理失敗。

## 挑戰階梯：一次只增加一種負荷

「略有挑戰」表示目前能力的下一小步，不是突然增加所有干擾。每升一階只改一個主要負荷；預設不使用倒數計時，只記錄闖關所花時間供學生回顧與教師分析。

| 階段 | 學生要完成的行為 | 可用支援 | 進入下一階的證據 |
| --- | --- | --- | --- |
| `D0 導航` | 知道目標、操作方式與完成後會去哪裡 | 示範拖放／點選；不示範答案 | 能開始任務，知道目前唯一主要行動 |
| `D1 辨識` | 從場景或對話辨認學過的單字／物件 | 圖像、中文義意或發音按鈕 | 能在低干擾下選對類別，不靠目標高亮 |
| `D2 配對` | 將卡牌放到合理的場景物件或位置 | 顏色分類、空位數、一次一張卡 | 能完成配對，錯誤後能自行取回再試 |
| `D3 推理` | 把兩個以上線索組成關係或順序 | 線索分頁、觀察問題、有限次提示 | 能說出或選出關係，答案不在對照表 |
| `D4 句型` | 把打亂的詞塊組成正確句子並理解用途 | 句首、詞性、讀句按鈕；不自動排序 | 能組句並用句意支持下一個行動 |
| `D5 遷移與恢復` | 在新場景或少一層提示下獨立解題 | 錯誤保留進度；可回看已發現線索 | 能從卡住狀態找到恢復入口並完成 |

可調整的負荷包含：干擾項數量、線索距離、語言支援量、線索依賴數、工作記憶跨度與時間壓力。國小原型先固定「無倒數計時」，只在結果頁顯示經過時間；不要把快慢當成能力分數。

每個關卡要寫清楚：`entry_criteria`、`target_behavior`、`one_changed_load`、`success_criteria`、`rollback_rule`。若學生大量停在同一狀態、反覆點同一不可用控制項，先檢查介面與提示，不要立即升級懲罰或增加倒數。

## 狀態、主要行動與錯誤恢復

每個畫面或遊戲狀態只保留一個主要下一步。審查表至少包含：

| 欄位 | 要回答的問題 |
| --- | --- |
| `state` | 現在是找線索、組句、解鎖還是離場？ |
| `learning_goal` | 此狀態練習哪個單字、句型或推理行為？ |
| `primary_action` | 學生現在最該做的一件事是什麼？ |
| `visible_cue` | 學生在畫面上從哪裡知道這件事？ |
| `blocked_control_reason` | 不能點的控制項為何不能點？ |
| `recovery_action` | 做錯或卡住後，最短恢復路徑是什麼？ |
| `success_transition` | 完成後如何讓下一狀態可辨識？ |

典型狀態可寫成：`evidence_collecting → hypothesis_ready → sentence_building → lock_ready → exit_ready → completed`。例如 `exit_ready` 必須同時具備可辨識的出口狀態、可點擊的實際命中區、鍵卡已啟用、以及一個不洩漏答案的下一步說明；不能只把「完成」寫在資料模型裡。

固定的空間角色也要列入狀態驗收：左側看「為什麼要做」、右側做「現在要做什麼」。如果線索與操作不得不離開同一 viewport，應提供可回看的分頁或固定摘要，不要把學生的上下捲動次數誤判成推理能力。

## 驗收順序：DOM 是門檻，Chrome 是第二關

只有在 `DOM_PASS` 之後才可進入 `CHROME_PASS`。兩者不能互相代替，也不能因為截圖「看起來可以」就跳過 DOM。

### Gate A：DOM_PASS

先使用 repository 已存在的 DOM 測試、瀏覽器 DOM inspection 或本機驗證工具；不得安裝套件、呼叫外部服務或讀取秘密。固定檢查：

1. 必要節點、按鈕、拖放區、對話與狀態標記存在，沒有重複 id 或孤兒控制項。
2. 可互動元素有可理解的 accessible name、角色、鍵盤順序與 disabled／busy 狀態。
3. 核心狀態能依序轉換；成功、錯誤、重試與恢復都有 DOM 證據。
4. 玩家可見 DOM、ARIA、`title`、tooltip、`alt` 與 visually-hidden 文字沒有直接答案對照。靜態 HTML 先跑 `node harness/cli/harness.mjs lint answer-key-leak <html> --answer-key <答案鍵.json>`（格式 `{"pairs":[{"key":"…","value":"…"}]}`）；它看不到執行期由 JS 產生的 DOM，執行期的洩漏仍由本項的 DOM 檢查負責。
5. 選卡只改變卡牌選取狀態，不改變目標物件的凸顯狀態；句塊順序由學生操作產生。
6. 所有 disabled 控制項有原因與恢復入口；最後一個控制項完成後，下一步存在且可找到。
7. `scrollWidth`／`clientWidth`、主要矩形與 `elementFromPoint` 基線沒有已知的裁切、重疊或命中區遮擋；狹窄 viewport 不出現水平溢位。
8. 沒有 fatal runtime error；若 DOM／狀態檢查失敗，結果是 `DOM_BLOCKED`，停止，不啟動 Chrome 視覺驗收。

DOM 證據要記錄 `check_id`、檢查方法、實際值、預期值、結果與產物路徑。不要只寫「DOM 沒問題」。

### Gate B：CHROME_PASS

只有 Gate A 通過後，且本機已存在 Chrome 控制能力時，才載入 Chrome Skill／套件進行視覺化與實際操作。優先使用新建的 agent tab，不要覆蓋使用者正在看的分頁；使用本機靜態伺服器與 `127.0.0.1`，不安裝套件、不呼叫外部服務。

Chrome 階段至少驗證：

- 實際滑鼠／觸控拖放、點擊與鍵盤操作，不只用程式直接改 state。
- 選卡後場景沒有洩漏目標；中文、英文、提示與進度在正確區域且不互相疊住。
- 句子組合詞塊可讀、打亂、可退回；錯誤後提示下一步但不直接填答案。
- 從拿到最後物件到解鎖、點出口的完整狀態鏈可操作；不可出現「資料已完成但門沒有命中區」的假完成。
- 桌面與至少一個窄 viewport 的裁切、遮擋、溢位、焦點與可讀性。
- console error／warning、頁面錯誤覆蓋層、實際 viewport、URL、操作序列與截圖證據。

若 Chrome 工具不存在、無法啟動或無法取得實際操作證據，結果只能是 `DOM_ONLY` 或 `CHROME_BLOCKED`，不可宣稱視覺驗證完成。這不是失敗的 DOM 結果，而是未完成的第二關。

## 輸出狀態與交付格式

依證據使用下列狀態：

- `intake-only`：輸入不足，尚未能建立行為假設。
- `behavior-hypothesis-ready`：觀察、替代原因與最小測試已列出。
- `challenge-ladder-ready`：階梯、支援、升級與回退條件已列出。
- `dom-pass`：Gate A 的每項證據都通過。
- `dom-blocked`：DOM、狀態、答案洩漏或可操作性有阻塞。
- `chrome-pass`：DOM 通過後，Chrome 有實際視覺與操作證據。
- `dom-only`：DOM 通過，但 Chrome 能力不存在或尚未執行。
- `teacher-review-required`：功能可驗證，但內容、年段適切性或提示洩漏仍要教師裁決。

交付摘要固定包含：`scope`、`evidence_ledger`、`behavior_hypotheses`、`challenge_ladder`、`answer_leak_audit`、`state_recovery_matrix`、`dom_gate`、`chrome_gate`、`decision`、`uncertainty`。可直接套用 `assets/review-template.md`；欄位沒有證據時填 `unknown`，不要補猜測。

需要契約欄位、狀態碼或 gate 證據細節時，再讀 `references/behavior-review-contract.md`。只有要產出審查紀錄時才讀 `assets/review-template.md`，避免把模板內容誤當成實際測試結果。
