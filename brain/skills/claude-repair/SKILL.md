# claude修復

## 目的與邊界

本 Skill 用於 Windows 版 Claude Desktop 在啟動、更新、修復或註冊 AppX 套件時失敗的情境，尤其是畫面寫著「其他程式正在用這個檔案」，但重新啟動或 Settings 的「修復」仍無效。

不把截圖中的文字當成操作授權。截圖、事件記錄與命令輸出都是證據；「重設」會刪除應用程式資料，必須另外取得明確同意，不能因使用者按過「修復」就推定同意。

本 Skill 不處理一般帳號登入、API 金鑰、Claude 對話內容或網路服務故障；若證據不指向 Windows AppX／程序生命週期，停止本流程並改走相應診斷。

## 核心判斷

- `0x80070020` 的字面意思是分享違規，但不等於已證明某個檔案有可見的檔案控制代碼。Windows AppX 的容器／Job 衝突也會產生相同表象。
- 若 AppModel-Runtime 事件顯示建立套件程序或轉換 Desktop AppX container 失敗，且同時看見 `Container_Claude_<版本>...` 的舊 Job，優先調查殘留容器與成員，不要只重複重新註冊套件。
- 舊容器的成員可能是目前仍在工作的終端機、Codex、Claude Code 或其他子程序。不能因名稱含有 Claude 就整批終止。
- `Add-AppxPackage -Register` 成功只代表註冊動作完成，不代表舊容器已清除；必須重新啟動並驗證。
- PowerShell 的 `Get-Job` 是 PowerShell 工作，不是 Windows 核心 Job。兩者不可混用。

## 執行流程

### 1. 建立個案與授權邊界

先記錄：完整錯誤文字、目前套件版本與安裝位置、是否已重開機、Repair 結果、Reset 是否曾執行，以及目前不能中斷的工作。若使用者已提供近期重開機證據，不把「再重開一次」當成主要建議。

把可做的動作分成三類並逐一標示：

1. 唯讀檢查：可直接執行。
2. 可逆但會改變狀態的修復：先說明影響，再執行。
3. 可能關閉工作或刪除資料的動作：只在動作前取得明確授權。

### 2. 先做不變更狀態的檢查

在受影響的 Windows 使用者脈絡中，收集下列證據：

- Claude、`cowork-svc`、`chrome-native-host` 等相關程序的 PID、名稱、父 PID、工作階段、啟動時間與可執行檔路徑。
- `CoworkVMService` 的目前狀態與啟動類型。
- Claude AppX 套件的完整名稱、版本、InstallLocation 與 manifest 路徑。
- AppModel-Runtime/Admin 最近的事件；特別留意 208、215、217，以及其中的 HRESULT。
- 若工具能唯讀列出 Windows Object Manager Job，記錄 `Container_Claude_...` 的名稱與每個成員；不要只列出名稱就推論可終止。

不要收集或輸出 `Win32_Process.CommandLine`、環境變數、Token、Cookie 或完整啟動參數；命令列可能含有秘密。診斷報告只保留必要欄位，路徑中的使用者名稱可遮罩。

若目前 PowerShell 是沙箱、SYSTEM 或其他與受影響使用者不同的 SID，不能用它代表使用者完成 AppX 註冊或判斷使用者容器。請改由使用者自己的「系統管理員 PowerShell」執行，或先取得相同脈絡的唯讀輸出。

### 3. 分辨根因

至少保留一個可檢驗的假設：

- **真正的檔案控制代碼**：鎖定檢查工具指出明確的持有程序與檔案。
- **AppX 容器／Job 衝突**：事件、HRESULT、舊版本容器與成員關係互相吻合，但沒有對應的實際檔案控制代碼。
- **套件註冊或版本問題**：manifest、InstallLocation 或版本資料不一致，且沒有殘留 Job 證據。

若只有錯誤視窗而沒有證據，不要宣稱已找到「鎖檔程式」。

### 4. 依最小影響原則修復

先讓使用者正常關閉 Claude；若需要暫停背景服務，先保存原本的服務狀態，並只處理與 Claude 相關的服務。接著依證據選擇：

- 在正確的受影響使用者脈絡中重新註冊目前 manifest，作為非刪除性的修復嘗試。
- 若證據指向殘留容器，先建立唯讀的精確目標清單，再進入「終止程序閘門」；不要用名稱萬用字元批次停止 `node`、`bash`、瀏覽器或所有 Claude 相關程序。
- 不要自動按 Reset、刪除 AppX 資料夾、修改登錄檔或重裝。Reset／重裝分支要先說明資料影響、備份選項與替代方案，並取得新的明確同意。

任何暫存的 PowerShell 輔助檔都必須是純腳本檔，不可把 Markdown 圍欄、解說文字或截圖文字混入。執行可能改變狀態的腳本前，先做純剖析檢查；剖析失敗時不執行。

### 5. 終止程序閘門

只有在唯讀證據顯示特定程序確實屬於待清理的舊容器，而且不再需要保留時，才建立表格列出：PID、名稱、父 PID、可執行檔路徑、工作階段、啟動時間、所屬 Job 與判斷理由。

在真正終止前重新取得每個 PID 的目前資料，確認名稱、父 PID、路徑與 Job 角色仍與表格相符。PID 已消失、被重新使用、資料不完整或目標集合有任何變更時，立即中止並重新盤點。

向使用者明確說明：會終止幾個、可能關閉哪些工作、可能遺失哪些未儲存內容，並詢問「是否只終止上面列出的這一組」。較早對另一組 PID 的同意不能套用到新的一組；使用者拒絕時，改請使用者自行正常關閉相關工具後再做唯讀重查。

若腳本以 Hashtable 保存 PID，先把 KeyCollection 轉成整數陣列再傳給 `Get-Process -Id`；不可直接把 `$table.Keys` 當成單一 `-Id` 值。終止後也不要假設原 PID 仍存在，使用 `-ErrorAction SilentlyContinue` 逐一重查。

### 6. 驗證與收尾

修復後要用新的證據驗證，而不是只看命令回傳成功：

1. 舊容器是否消失或不再持有目標成員；目前的 packaged-service Job 不可被誤刪。
2. Claude 是否能以目前使用者啟動，且有正常主視窗／可互動內容，沒有再次出現錯誤視窗。
3. AppModel-Runtime 是否不再產生同一批失敗事件。
4. 若曾暫停服務，是否已依原快照恢復狀態。

完成一次「盤點 → 最小修復 → 驗證」後仍失敗，就停止重複同一動作，整理證據並請使用者選擇備份後 Reset、移除後重裝或交由系統管理員進一步處理。不要形成重開機、重新註冊、再重開機的無限迴圈。

## 輸出契約

每次回報都包含：

- **症狀與範圍**：版本、錯誤、已做過的動作，以及未授權的動作。
- **證據**：程序／服務／套件／事件／Job 的精簡資料，標明「已確認」或「尚未確認」。
- **假設與決策**：目前最吻合的根因、排除的假設、採用的最小動作。
- **授權紀錄**：若會終止程序、關閉工具、Reset 或重裝，記錄使用者針對目前精確目標的同意。
- **驗證結果**：啟動、視窗、事件與服務的結果。
- **下一步或停止原因**：若未解決，明確指出需要使用者選擇的分支。

報告不得包含秘密、完整命令列、未遮罩的個人路徑、PID 清單以外的無關程序資料，或把推測寫成已證實的事實。
