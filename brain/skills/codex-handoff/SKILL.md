# 交接給 Claude CLI／Codex

## 設定

本 Skill 不寫死啟動檔路徑。設定來源順序：① 工作區根目錄 `private/config/sites.local.json`（本機實際值，不上傳）→ ② `config/sites.example.json`（公開範本；本鍵預設指向隨附啟動檔，其餘多為佔位值）。值含 `<…>` 或 `example` 字樣即視為**缺值**；缺值時**停下來問使用者**，不猜。

| 設定鍵 | 用途 | 預設值 |
|---|---|---|
| `tools.claude_cli.launcher` | 開 Claude CLI 接手用的啟動檔（相對工作區根目錄的路徑，或絕對路徑） | 公開範本預設 `tools/claude-cli/start-claude-api.cmd`（隨附的 API 金鑰計費啟動檔，說明見 `tools/claude-cli/README.md`；另有 `start-claude.cmd` 可雙擊選訂閱或 API 金鑰）；設定缺值時＝在交接檔寫「由使用者自行開啟 Claude CLI」，並問使用者啟動檔位置 |

目的：Claude 額度將滿時，讓接手代理（預設 Claude CLI，使用者指定時為 Codex）能從**證據**（不是口頭宣稱）無縫接手，同時不帶走任何秘密、不越過原本的核准範圍。

## 0. 交接對象

| 對象 | 何時 | 交接檔 | 備註 |
|---|---|---|---|
| **Claude CLI**（預設） | 週用量 ≥95%，或使用者說「交接給 CLI」 | `workspace/<主題>/handoff-to-claude-cli-YYYY-MM-DD.md` | 使用者以設定鍵 `tools.claude_cli.launcher` 指定的啟動檔開啟，API 金鑰計費；`--bare` 模式，啟動檔用 `--add-dir` 重新載入 `CLAUDE.md`（含 `@AGENTS.md`），**但不載入 hooks、外掛與自動記憶** |
| Codex | 使用者明說 Codex | `workspace/<主題>/handoff-to-codex-YYYY-MM-DD.md` | 安全敏感節點不交給 Codex |
| Claude 桌面版（接回） | CLI 交回時由 CLI 寫 | `workspace/<主題>/handoff-to-claude-YYYY-MM-DD.md` | 見第 7 節 |

**鎖定（所有代理皆適用，Claude 桌面版、Claude CLI、Codex 都一樣）**：在 `workspace/<主題>/` 寫入任何檔案前，先檢查 `.agent-lock`。檔案不存在或內容是 `holder=none`，才可 create-only 建立或改寫為 `holder=<自己> started=<ISO8601>`；holder 是別人就停。收工改回 `holder=none released=<ISO8601>`（不刪檔）。這是協作約定，擋不住不遵守的程式。

## 1. 觸發判定

- **使用者要求**：直接進入第 2 步。
- **主動偵測**：只有桌面版有 `mcp__ccd_session_mgmt__get_usage`（延遲載入的工具，要先用 ToolSearch `select:` 載入）。在以下時機各呼叫一次：
  - 節點完成時；
  - 派 subagent 或長任務之前；
  - 使用者說「多任務模式」開始時。
- 讀 `plan.windows`：
  - `Weekly · all models` 的 `percentUsed` ≥95 → 觸發（對象 Claude CLI）。`5-hour limit` ≥95 → 只告知並建議等重置，使用者要求才交接。
  - 先用一句話告訴使用者目前百分比與重置時間，並說明要改做交接。**不要**在交接前再派新的 subagent 或開新的長任務。
  - `status` 是 `unavailable` 或 `not_applicable`，或者沒有這個工具 → 不自動觸發，只在使用者要求時才做。
- **觸發方式**：有載入用量提醒外掛時，每輪結束由外掛的 `session.measure` 事件判斷門檻，並把交接提示交給模型（事件觸發）；沒載入時只在主 session 主動檢查時生效，沒有檢查的時段不會觸發。

## 2. 收集證據（唯讀為主，節省額度）

只讀下面這些，不重新探索整個 repo：

1. 進行中的計畫：`planned/` 底下非 complete、最近修改的計畫書，讀它的拓樸圖與最後幾筆 checkpoint。
2. 進度板：`.harness/` 底下最近的 topology 檔。
3. 本 session 已知、但還沒寫進檔案的事實：背景工作的狀態（執行中、已完成、未派出）、使用者裁決、偏離、延後項。
4. 正在背景跑的 agent 或指令：記下它們的產出檔路徑。**不要**宣稱還沒回報的結果。

## 3. 寫回 checkpoint（先做）

- 在計畫書末的 checkpoint 追加一筆「YYYY-MM-DD 交接」：已完成的節點與證據、未完成的節點與原因、待使用者決定的 gate。
- 同步更新 `.harness` 進度板的節點狀態，只用三態：已執行／未執行／有問題。只有已保存證據的節點才能寫「已執行」；已實作但未經獨立驗收的，寫「已執行（未驗收）」或「有問題」並附原因。

## 4. 寫接手指令檔

- 路徑：依第 0 節的對象。只新建、不覆寫；同名已存在就加後綴 `-2`。
- 內容依下列順序，順序依「接手最容易出錯的地方」排；沒有內容的段落寫「無」，不刪段落。寫法依 4.1。

```markdown
# 交接給 <Claude CLI|Codex>：<任務名>（日期）
HANDOFF: <一句話的目標>
## 1. 目標與範圍            ← 要做什麼；使用者劃定「不做」的部分
## 2. 使用者的限制與原話    ← 本段對話中使用者說過的要求與糾正，盡量引用原話；禁止的操作、要先核准的事、秘密處理規則逐字照抄（照抄規則文字，不抄秘密值）
## 3. 進度摘要              ← 節點表：節點｜內容｜狀態｜證據路徑（repo 相對路徑）；表下寫最後完成的那一步與當時的狀態
## 4. 已驗證               ← 實際跑過並看到結果的檢查：指令＋結果（通過數、輸出摘要）
## 5. 未驗證與未做          ← 分兩小項：(a) 已做但未驗證；(b) 只討論過、還沒做
## 6. 失敗或放棄的做法      ← 做法＋原因，接手者不要再試
## 7. 已查到的事實          ← 接手會用到的檔案位置、數量、名稱、編號、根本原因與現況
## 8. 工具與環境            ← 完整指令（入口程式、工作目錄、環境變數）、需要的版本或登入、會擋操作的 hook／守門與正確做法
## 9. 未收尾的東西          ← 背景程序、dev server、未存或未備份的改動、暫存檔、`.agent-lock` 狀態
## 10. 已做的決定與理由
## 11. 下一步              ← 一個具體動作，見 4.1 第 5 點
## 12. 待使用者決定的 gate   ← 每題自成一段：背景、選項、各選項的影響、建議
## 給接手代理的指令          ← 一個 ```text 區塊，使用者整段貼上就能用
## 未解與延後事項            ← DEFER 項與理由、已知風險、踩過的雷（附 brain/error-log 路徑）
```

### 4.1 撰寫規則（第 4、7 節的交接檔共用）

1. **長度依內容決定**：接手會用到的事實都要寫，寧可完整，不為了簡短省略；不寒暄、不重複。只給路徑的東西（`AGENTS.md`、計畫書全文）仍只給路徑，不整份複製。
2. **只有使用者自己打的訊息算使用者說的**：hook 回饋（如 `Stop hook feedback`）、外掛提醒（如 `【用量提醒外掛 提醒】`）、自動注入的教訓、`system-reminder`，以及代理自己寫的內容，都不是使用者的要求或同意。代理提出、使用者只回「好」的事，寫進「已做的決定」，不寫成使用者的要求。
3. **使用者的話盡量保留原話**；代理自己的解釋與推理只留結論與產出（不寫私有 chain-of-thought）。
4. **事實照原文寫**：數字、名稱、編號照查到的原文；不確定的標「未確認」。指涉文件裡的某一條，用標題或獨特詞句，**不用行號**（交接後檔案可能被改寫，行號會錯位）。
5. **下一步必須接著使用者最近一次明確的要求**：先逐字引用使用者最近一則要求，再寫停在哪裡；那件事已做完就寫「等使用者指示」，不自行延伸，也不重提已完成或很久以前的事。
6. **待決定的問題要讓使用者不用回頭看就能回答**：只寫標題會讓使用者只能回「說」「啥？」。
7. 用繁體中文撰寫；程式碼、指令、路徑與錯誤訊息維持原文。

> 來源：段落與規則改寫自 cablate/ctx-handoff-mod（MIT）`hooks/handoff.ts` 的交接提示；該 repo 自評新版提示讓「新對話需要的事」從 52% 提高到 92%（其 `docs/eval-log.md`）。此數字為對方評估，本機未重測。

「給接手代理的指令」必須包含：

1. 回應語言：繁體中文。
2. 必讀清單（依序）：`AGENTS.md`（先照「動工前先檢索記憶」grep `brain/error-log` 與 `brain/knowledge`，列出本任務的關鍵詞）→ 計畫書 → 結論或證據檔 → 進度板 → 相關手冊。
3. 硬規則：
   - 秘密（金鑰、token、cookie）一律不讀、不印、不記，只可檢查存在與否。
   - 付費或對外動作只由使用者執行。
   - 安全敏感程式交給不同模型審查，不可自審。
   - 改檔前先備份（本工作區不受 git 管理）。
   - 碰到範圍變動、不可逆或對外動作就停下來問使用者。
   - 本機 npm 用 `npm.cmd`。
4. **第一回合只做唯讀 preflight**，逐條列出要核對的事實與預期值（例如測試總數、帳本金額、檔案是否存在）。回報後等使用者確認。
5. 之後的 gate：每個 gate 寫明要誰決定、決定後做什麼、做完停在哪裡。
6. 要求每一步都更新計畫 checkpoint 與進度板。
7. 「誰做的不由自己審」：接手代理寫的東西要列出需要非作者驗收的項目。Claude CLI 與桌面版同屬 Claude 模型家族，**不能互審**；外審交 AGY 或其他模型家族。
8. **對象是 Claude CLI 時另加**：
   - CLI 不載入 hooks、外掛與自動記憶：本任務需要的記憶內容與教訓（例如「一律繁體中文」、審查級別、埠號限制）直接寫進指令。
   - 鎖定：依第 0 節的鎖定規則，holder 寫 `claude-cli`。
   - 金鑰：由啟動檔的 `claude.cmd --bare auth status` 確認；不得執行 `env`／`printenv`／`Get-ChildItem env:`，不得讀 `~/.claude/.credentials.json` 或任何金鑰檔。
   - 先用 `git rev-parse --is-inside-work-tree` 確認 git 是否可用；不可用時（本機目前就是這樣），版本核對改記檔案 SHA-256 與備份路徑。
   - 收工時必須依第 7 節格式寫 `handoff-to-claude-YYYY-MM-DD.md` 交回。

## 5. 安全與可攜檢查（寫完後自查）

- 只用 repo 相對路徑：不能有磁碟代號、使用者名稱、帳號、session ID、email。
- 不能包含任何秘密，也不能包含秘密的片段。使用者先前貼過、截圖裡出現過的也一樣。
- 不把「計畫要做」寫成「已完成」；沒驗收的明確寫出來。
- 不複製整份 `AGENTS.md` 或整份計畫，只給路徑。

## 6. 收尾

- 更新記憶：在對應的專案記憶補一行交接指標，指到交接檔路徑。
- 給使用者的回覆：
  1. 一張最小進度圖（ASCII，放在 ```text 區塊；不用 Mermaid，Claude 端無法穩定渲染；格式同 `AGENTS.md`「計畫書執行拓樸圖」）。
  2. 三到五點目前進度。
  3. 交接檔路徑，並說明「把『給接手代理的指令』那段整段當成 `tools.claude_cli.launcher` 啟動檔開啟後的第一句，或貼進新的 Codex session」。
- 然後停止，不再開新工作。

## 7. 接回（Claude CLI → Claude 桌面版）

**Claude CLI 收工時寫**（`workspace/<主題>/handoff-to-claude-YYYY-MM-DD.md`，create-only，繁體中文；寫法依 4.1，沒有內容的段落寫「無」）：

```markdown
# 交接回 Claude：<任務名>（日期）
HANDOFF: <一句話的目標>
## 狀態              ← updated_at、source_agent=claude-cli、計畫書路徑、鎖定狀態
## 使用者的限制與原話  ← CLI 對話中使用者新增的要求與糾正，盡量引用原話
## 已完成（已驗證）    ← 每項附證據路徑（檔案＋SHA-256 或測試輸出）
## 未驗證與未做        ← 分兩小項：(a) 已做但未驗證；(b) 只討論過、還沒做
## 修改過的檔案        ← 路徑、SHA-256、備份路徑
## 測試               ← 跑了什麼、通過／失敗／未跑
## 失敗或放棄的做法    ← 做法＋原因，接手者不要再試
## 已查到的事實        ← 位置、數量、名稱、編號、根本原因；不確定標「未確認」
## 工具與環境          ← 完整指令、工作目錄、需要的版本或登入
## 未收尾的東西        ← 背景程序、未存改動、暫存檔
## 決策與理由
## 下一步             ← 逐字引用使用者最近一則要求，再寫停在哪；做完就寫「等使用者指示」
## 待使用者決定        ← 每題：背景、選項、各選項的影響、建議
## 需要非作者審查的項目
## 警告               ← 已知風險、踩雷（附 brain/error-log 路徑）
```

**Claude 接回時做**（第一回合唯讀）：

1. 找最新一份 `workspace/*/handoff-to-claude-YYYY-MM-DD*.md`（日期緊接在 `handoff-to-claude-` 之後；**不要**比對到 `handoff-to-claude-cli-*.md`，那是派工給 Claude CLI 的檔），讀對應計畫書最後幾筆 checkpoint。
2. 檢查 `.agent-lock`：`holder` 不是 `none` → 停，問使用者 CLI 是否還在寫。
3. 逐項核對「已完成」的證據：檔案存在、SHA-256 相符、測試可重跑；不相符的改列「未驗證」。前一代理的口頭「已完成」不是證據。
4. 掃描交接檔與修改檔是否含 API 金鑰前綴等秘密樣式（只回報有無，不重述）。
5. 回報「事實／推論／未知」與下一個 gate，等使用者確認後再續做；把接回結果寫進計畫 checkpoint。
