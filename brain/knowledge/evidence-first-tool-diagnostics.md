# 證據優先的工具診斷規則

## 核心規則

工具的 `status=SUCCESS` 只表示呼叫層完成，不表示任務完成。任務完成必須同時有非空、切題、涵蓋指定範圍的產物。

任何工具故障診斷都必須先分成三層：

- **事實**：工具回傳的原始欄位、錯誤碼、拒絕動作、輸出內容。
- **推論**：由事實支持的可能原因，標示信心，不得寫成事實。
- **未知**：目前沒有直接證據的部分，保留為未知。

## 四道證據閘門

1. 讀完整回傳：`status`、`response`、`error`、`warnings`、`denied_actions`、是否截斷。
2. 分類錯誤：身分驗證、工具策略、參數／格式、逾時／崩潰、結果缺失。
3. 做反事實檢查：若要說是登入失敗，必須有 401、`AUTH_EXPIRED`、`LoginRequired` 或工具明示的身分錯誤；空回應或 `denied_actions=command` 不足以支持這個結論。
4. 選擇下一步：有已授權替代方式就用不同策略重試；沒有替代方式就回報 `INCONCLUSIVE`，不能補寫原因。

## 重試與停下來的規則

- `command` 被拒、但 `read_file` 可用：保留原任務與範圍，改為明確只使用 `read_file` 重試一次。
- 同一策略原樣重試：禁止。
- 替代方式仍空白、被拒，或資訊互相矛盾：停止並列出事實、未知與可選驗證步驟。
- 只有看到明確身分錯誤，才可以要求使用者登入或處理帳號權限；即使有 `401`，也要先確認它屬於哪個服務與哪個身分層，不能直接等同於使用者未登入。

## 使用者提出反證時

若使用者說「之前同樣方式可以用」，這是新的反證。必須重新檢查工具輸出與呼叫差異，不能把原先的推論重複一次，也不能要求使用者先做同一個未被證明必要的動作。

## 最低驗收標準

1. 輸入 `SUCCESS + 空 response + denied_actions=command` 時，不得輸出「未登入」或「請重新登入」。
2. 必須輸出「已知事實／目前推論／未知」三欄或等價內容。
3. 若 `read_file` 是已知可用替代方式，必須先自動降級重試。
4. 替代重試成功後，必須檢查產物是否真的涵蓋原任務，不能只看 `status=SUCCESS`。
5. 找不到直接證據時，對「原因」的結論只能是 `INCONCLUSIVE`；若替代方式已完成原任務，可以判定任務完成，但仍須保留原先原因未知。
