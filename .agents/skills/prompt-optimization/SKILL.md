# 提示詞優化

## 定位

本 skill 是「提示詞診斷、最小幅度重寫與交接契約」閘門，不是自動換模型、安裝工具或替使用者擴大任務範圍。它以官方 GPT-5.6 Sol 提示指南為設計參考，適用於 system prompt、agent 指令、工具說明與提示堆疊；不宣稱其他模型必然有相同表現。

## 何時啟動

在任務路由最前面檢查下列條件：

### 明確觸發

- 使用者說「提示詞優化」「優化這段 prompt」「重寫 system prompt」「改善指令」「prompt guidance」或要求提示詞遷移。
- 使用者要求把一段自然語言轉成可交給 Claude、Codex 或 agent 的執行提示。

### 隱性觸發（實質不明確）

只要缺漏或互相衝突的資訊足以改變執行結果，就啟動一次介入，例如：

- 目標、交付物、受眾、範圍或完成標準不明。
- 約束、證據來源、權限、是否允許外部寫入／刪除／花費未定。
- 工具、資料位置、模型／平台路由、停止條件或驗證方式不明。
- 使用者要求與既有工作區安全規則、檔案範圍或前後文互相矛盾。

### 不啟動

- 已有明確目標、輸出、範圍與驗證方式的單一步驟請求。
- 只有錯字、語氣或排版潤飾，且不會改變任務語義。
- 單純詢問事實，沒有要改寫提示或執行不明確動作。

若只是非關鍵細節缺漏，列出明確假設後繼續；若缺漏會導致不同的外部動作、資料變更或交付物，先提出最少量澄清問題。不得默默替換使用者意圖。

## 工作流程

1. **分類意圖**：標記為回答、解釋、審查、診斷、規劃、修改或建置；回答／審查／診斷／規劃不因提示優化而自動取得實作授權。
2. **保留原要求**：抽取語言、格式、受眾、範圍、期限、指定模型／平台、不可做事項與使用者價值排序。
3. **找出缺口與衝突**：以證據標記 `✅已確認`、`⚠️推測`、`⏳待確認`、`❓未提及`、`❌已否定`、`❗來源衝突`；沒有證據不補寫成事實。
4. **最小幅度優化**：保留結果與真正不變的規則，刪除重複規則、過時範例與不相關工具；只有真正不變的條件才使用「必須／不得／只能」。
5. **產生候選提示**：依「角色、個性（需要時）、目標、成功標準、限制與權限、證據、工具、輸出、停止規則」排序。
6. **確認閘門**：若候選提示會改變範圍、外部寫入、刪除、付費、發布或模型路由，先交由使用者確認；安全且不擴張範圍的局部澄清可直接繼續，但要揭露假設。
7. **交接與驗證**：將優化後提示、未決問題、`requestedModel`／`actualModel`、工具前置條件與驗證案例交給下一個 agent；不得把提示改寫當作已完成任務。

## 候選提示格式

```text
角色：<必要的專業角色>
個性：<只有會影響合作方式時才填>
目標：<可觀察的結果與範圍>
成功標準：<可驗證的完成條件>
限制與權限：<安全、商務、資料、使用者授權與不可做事項>
證據：<可使用的來源、引用要求、證據不足時的處理>
工具：<僅列任務相關工具與前置條件；獨立讀取可並行>
輸出：<語言、格式、欄位、長度、受眾與交付位置>
停止規則：<何時停止；缺證據時如何回報；何時交回使用者>
```

## 回覆契約

觸發後先回傳精簡的「提示詞優化介入」區塊，至少包含：

1. `status`：`clear`、`needs-optimization` 或 `blocked`。
2. 啟動原因與缺口證據；明確區分已確認、假設與待確認。
3. 優化後提示（若使用者只要求分析，標為候選稿，不直接取代原提示）。
4. 變更表：原意／修改／理由／可能風險。
5. 未決問題與所採假設。
6. 最小驗證計畫與代表性評估案例。
7. 交接欄位：`requestedModel`、`actualModel`、`availability`、`fallbackReason`、`approvalRequired`。

若使用者明確要求「直接執行」且不涉及額外權限，提示優化完成後可進入原任務；若需要外部協調或高風險寫入，仍須停在確認閘門。

## 複雜計畫與雙平台規則

- 架構、跨專案、多檔案、不可逆變更或反覆失敗的複雜計畫，先由 `codex-sol`（high）設計，再由 `claude-fable` 審查一次。
- 審查輸出必須列出同意理由、不同意理由、證據、替代方案與需使用者裁決之處；不得用 Codex 文字冒充 Claude 立場。
- 任一平台因額度、登入或執行面不可用時，記錄 `unavailable` 與原因，交由使用者選擇單一平台處理或延後；不可假造雙平台完成。
- 不預設呼叫 Sol subagent；模型與 agent 由 harness 的 task packet 路由，並保留要求模型與實際模型的差異。

## 工作區整合規則

- 正常文件輸入先遵循 MarkItDown 轉 Markdown 流程；論文格式／視覺審查例外，依論文 skill 保留原始版面。
- Brain Markdown 是知識 SSOT；BIRD 只負責知識定位與索引，不取代原文。提示優化產物放在 `planned/` 或指定專案，不把暫時推理寫入 Brain。
- 僅可讀取使用者授權的資料；不讀取或輸出 secrets、API key、Cookie、私鑰或其內容。

## 防誤用

- 不把「更詳細」誤解為「更好」；優先保留清楚的結果與停止條件。
- 不擴增新事實、受眾、工具、模型或交付格式；沒有來源的新增內容只能標為假設。
- 不輸出隱藏思考鏈；只提供可審查的理由、證據摘要與決策點。
- 不因提示優化自動安裝 plugin、skill、runtime 或切換工作磁碟。
